## The result — can agents really work the web at the same time?

Yes, with one deliberate exception, and it helps to name three different things people mean by "simultaneous":

1. **Parallel OS/browser control — YES, on exactly one path.** Two agents can each own a separate Chrome process with its own non-default user-data directory and act on their own exact tabs **through browser-native DOM/CDP page actions only** — that path never touches the shared desktop machinery, so two writers genuinely overlap. Anything routed through cua/AX/pointer/keyboard is **not** a parallel channel: Cua Driver 0.7.1 confirms all clients share one screen/keyboard/pointer/AX/recording surface and two agents clicking at once contend, so every desktop-level write on this machine serializes under a single machine-wide **desktop-control lease**. Parallel *browsing* is real; parallel *desktop input* is not.
2. **Brief serialized submission moments — the one exception.** Whether one Google account may safely have two automated surfaces *submitting* at the same instant is officially **UNKNOWN** — Deep Research documents concurrent research *jobs* up to a limit, but nothing covers two automated surfaces submitting at once, and Flow documents neither — and Flow/AI credits are **VERIFIED account-wide**: no local boundary, not even a VM, isolates quota. So the safe design serializes only the act of submission: one account-submission lease, held for the seconds it takes to press "generate" or "start research," then released.
3. **Server-side generation continues after submit — officially per-product; cross-product overlap not yet.** Once submitted, the work runs on Google's servers, not the Studio — and this is now official *per product*: Gemini Deep Research lists a limit on the "number of research requests you can run at the same time" (i.e. more than one, up to plan limits) and lets you leave the chat while a report runs; Flow documents background generation continuing after the mobile app closes and multi-variation output from a single request (evidence 15/16). What remains **UNKNOWN**: whether a Flow job and a Deep Research job may be active for one account at the same time (cross-product overlap), and how many *independent* Flow requests may run concurrently. Kun's C4 is zero-submission by design, so it validates only that two *isolated authenticated surfaces* can coexist safely — it cannot validate actual active-job overlap; that requires a separately gated, bounded **live** overlap canary after C0–C4 passes (Phase IV below). So serializing the submission moment still costs seconds and per-product background continuation is real, but full cross-product overlap is an expectation to validate, not a guarantee to assume.

On challenges: the only verified evidence that automation triggers unusual-traffic/CAPTCHA is for **Google Search, at the network/egress level**. Whether a Flow or Gemini challenge attaches to the account, the session, or the IP is **UNKNOWN** — so the policy freezes every lease sharing the same account **and** the same egress the moment any challenge or permission prompt appears, precisely because we cannot prove a smaller blast radius. That freeze is deliberately conservative, not a claim that challenges are account-scoped.

## Decision — minimum safe boundary for Flow + Gemini, and do the current scripts meet it?

**Minimum safe boundary (two driving agents, Flow + Gemini on one account): the profile boundary plus the broker, with all parallel writes on the DOM/CDP path.** Concretely: separate Chrome processes with distinct **non-default** user-data directories, one owned downloads directory per driver, exact CDP target-ID addressing, **parallel writes exclusively via browser-native DOM/CDP page actions, and every cua/AX/pointer/keyboard write serialized under the machine-wide desktop-control lease**, clipboard banned, no `activate`, all enforced by the single-writer broker/lease layer with fail-closed target re-verification (a client that cannot re-verify its target stops; it never falls back to the front window) — **plus account-level submission serialization and the same-account/shared-egress challenge freeze.** A separate OS user or VM is *not* the minimum: the profile boundary + DOM/CDP writes suffice mechanically, and no boundary isolates the account's quota anyway. An OS user/VM is the only boundary that would let two *cua* writers act simultaneously — unnecessary while writes go through DOM/CDP; escalate only if Kun's canaries show the cua path cannot be confined to the desktop-control lease or shared-desktop contention blocks the required reads.

**The current scripts meet none of this.** `flow_generator_batch.py` violates every clause of the replacement contract: front-window/active-tab targeting (banned — durable target IDs required), `activate` (banned — background input), `close every window` (banned — close the leased window only), global clipboard paste (banned — per-target text injection), global System Events keystrokes (banned — element-addressed input under lease), shared `~/Downloads` (banned — per-lease download dir). It also runs on the default Chrome profile — which does not break the existing AppleScript itself, but blocks the proposed migration: Chrome 136+ refuses remote-debugging/CDP attachment on the default data directory (and Playwright calls the default profile unsupported for automation), so the exact-target CDP replacement requires the new non-default profiles in any case. Tori's computer-use path is closer (background, per-PID) but lacks durable tab identity without CDP and carries the unresolved bridge-loss defect, which the new architecture converts from a silent hazard into a hard stop.

## What changes (contract-level; nothing changed yet)

The Flow driver is rewritten to the seven replacement clauses (R1–R7 in Lana §4: leased-window close, CDP-target addressing, no activate, leased element input, no clipboard, registered new windows, owned downloads). A small broker service holds the lease registry (target leases + global-resource leases + the account-submission lease + the machine-wide **desktop-control lease** that every cua/AX/pointer/keyboard write must hold — browser-native DOM/CDP writes are exempt and need only their target lease), with TTL/heartbeat/epoch fencing and an append-only audit journal. The rewritten driver prefers DOM/CDP input (replacement clause R4); any residual cua/AX step runs single-writer under the desktop-control lease. Tori's driver path gains CDP target identity on top of cua-driver's window addressing. Six FAIL_CLOSED_IMPACT items are on record (Lana §5) — notably that today's chaos accidentally serializes everything and true parallelism makes real races reachable on the DOM/CDP path, plus the late-evidence tightening F6: the earlier assumption of parallel background cua input is withdrawn, and cua-path throughput is single-writer by design — which is exactly why nothing goes live before the ladder.
