- **Profile/F,K,C:** a separate `user-data-dir` gives a separate process but stays in one macOS login session, so System Events keystrokes/clipboard/frontmost remain global (T3.2, T3.3, G5). Displays/Spaces likewise do not solve these (G5).

- **Context/S,A:** contexts isolate cookies/storage (ISO **A**, T2.1) yet share one browser owner/process (PART **S**: one persistent context per dir, T2.2).
- **Profile/R:** separate process → crash isolated; same bundle → auto-update shared (T1.5 UNKNOWN). Bundle/R and VM/R add update isolation.
- **OS-user/R:** separate session isolates crash; the shared `/Applications` bundle is still updated once (T1.5) → PART.
- **X (all boundaries):** here "NO" means *not proven isolated*, **not** *proven to collide*. Since no boundary is *proven* to isolate a challenge, it is scored conservatively as not-isolated. T5.1 (multiple-account/default-account ambiguity) is **not** evidence of challenge scope and is therefore not cited in this column.
- **F/K/C mechanism (cua vs DOM/CDP) — reads across the whole matrix:** the "avoided by *routing*" benefit (Context/K) holds **only** for browser-native DOM/CDP writes (the `page` tool, T4.5), which bypass the desktop machinery. It does **not** extend to cua/AX/pointer/keyboard: Cua Driver 0.7.1 confirms all MCP clients "share the same screen, keyboard, pointer, accessibility tree, and recording machinery" and "Two agents clicking at once still contend" (T4.1, T4.3). The **F/K/C = NO** scores are therefore *isolation* scores — they do not imply cua concurrency is safe once serialized, nor that DOM/CDP concurrency is unsafe.

**Two axes are NO for every boundary — the governing finding, though for different reasons.** Quota (**Q**) is **account-wide and VERIFIED**: credits are "shared across your account, regardless of which device you use" (T5.2), so no local boundary — up to and including a VM — isolates it. CAPTCHA/challenge blast radius (**X**) is a **different, weaker** case: its scope is **UNKNOWN** for Flow+Gemini. The only VERIFIED signal is that Google **Search** unusual-traffic/reCAPTCHA is triggered at the **network/egress** level (T5.4); whether a Flow/Gemini challenge attaches to the account, the session, or the egress IP is **not established** (T5.3, T5.4), and T5.1 (multiple-account/default-account ambiguity) says nothing about challenge scope. Because no boundary is *proven* to isolate a challenge, **X** is treated conservatively as not-isolated and — like **Q** — handled by *policy* (§3) rather than by a boundary. (A VM changes the egress IP, which T5.4 shows matters for Search traffic; whether that helps or hurts a Flow/Gemini challenge is unknown, so it is claimed as neither.)

**Corollary.** Focus/keystrokes/clipboard (**F/K/C**) are ISO only at OS-user/VM cost (G5) — *or* escaped by writing through **browser-native DOM/CDP** (the `page` tool), which never touches the shared desktop machinery (T4.5, T2.1, T1.4). This escape does **not** extend to cua/AX/pointer/keyboard: those share one screen/keyboard/pointer/AX/recording surface regardless of boundary (T4.1, T4.3), so the broker (§2) must **serialize every cua/desktop write under a single machine-wide desktop-control lease**. Net: the broker buys parallel *writes* only on the DOM/CDP path; the cua path stays correct but single-writer — avoiding the OS-user/VM tax for correctness, not for concurrency. Clipboard stays banned by default (T3.3). Singleton/auth (**S/A**) need the profile boundary; crash/update (**R**) needs the bundle boundary.

### Minimum sufficient boundary

**(a) Two read-only agents → window/target-scoped read addressing inside one shared instance, gated by a dual-observer soak canary.**
Observers issue no F/K/C writes and no submissions, so Q/X/K/C/F are not in play; a second launch on the same `user-data-dir` would anyway delegate to the singleton (T1.1), so they *share* one instance and address distinct windows/targets (T3.1 per-window AX; T1.4 CDP target-ids). The live risks are **R** (a crash of the shared instance takes both observers, T1.5) and reliability: even two *read-only* cua captures share the accessibility-tree and recording machinery (T4.1), multiple simultaneous AX clients is **UNKNOWN** (T3.5), and R1/R2 bridge loss is unresolved (G4, T4.4). Reads over **DOM/CDP** avoid the shared AX/recording surface (T4.5) and are the contention-free alternative where a page target suffices. → **Minimum = window/target read addressing (DOM/CDP where a page target suffices) under a hard no-write/no-activate/no-clipboard/no-keystroke rule, contingent on Kun's C0/C1/C2 receipts** — and, for concurrent *cua* captures, on the same desktop-control discipline. Until that canary is green, default to separate processes/profiles (cheap **R**+**S** isolation).

**(b) One driving + one reading → profile boundary (separate process + distinct non-default `user-data-dir`) + driver writes via DOM/CDP, else the desktop-control lease serializes the driver against the reader's capture.**
The driver must stay off the shared desktop surface: writing through browser-native DOM/CDP (`page` tool, T4.5) leaves the reader's AX/recording untouched, so the two can run concurrently. If the driver instead uses cua/AX/pointer/keyboard, it must hold the exclusive **desktop-control lease** (§2) — and while held, the reader's *cua* capture contends and is serialized behind it, because all clients share the pointer/AX/recording surface (T4.1, T4.3). `activate` stays banned; clipboard banned (T2.1). The axis (b) adds over (a) is **R**: a driver may `close`/navigate/crash, and on a *shared* process that corrupts the reader's target. Crash isolation requires a separate process, which — because one owner per `user-data-dir` (T1.1) and non-default dir needed for debugging (T1.3) — requires a distinct non-default `user-data-dir`. Session/auth isolation (**A**) comes free and keeps the reader off the driver's mutating cookies.

**(c) Two driving agents → per-driver profile boundary (separate process + distinct non-default `user-data-dir` + own downloads dir + exact CDP target-ids) writing through browser-native DOM/CDP, PLUS account-level submission serialization and a conservative same-account + shared-egress challenge freeze.**
Both write, so **S** (cannot share a dir, T1.1), **A**, and **R** must all be isolated (profile/process boundary), each driver owning its download dir (T2.5). **The only genuinely-parallel write path is browser-native DOM/CDP** (the `page` tool, T4.5): two drivers act at the same time *only* because CDP DOM actions never touch the shared screen/keyboard/pointer/AX (T4.1, T4.3). Any cua/AX/pointer/keyboard write is **not** parallelizable — "Two agents clicking at once still contend for the same desktop" (T4.3, evidence 20) — and is serialized machine-wide under the single **desktop-control lease** (§2). This refines Tori's downstream conclusion #1: separate processes/profiles are **necessary but not sufficient** for parallel writes; the DOM/CDP mechanism is the other half, and any cua step degrades two drivers to one-at-a-time. Beyond the machine boundary, **Q is account-wide and unsolved by any boundary** (T5.2, VERIFIED), and **X's scope is UNKNOWN** for Flow+Gemini (T5.3, T5.4) so no boundary can be *relied on* to isolate it — both are therefore covered by §3 policy, not by escalating the boundary. **Separate OS user / VM is *not* the minimum** — it neither is required (profile boundary + DOM/CDP writes suffice mechanically) nor isolates the account's quota (T5.2); it *is* the only boundary that would let two **cua** writers run at once, but that is not needed if writes go through DOM/CDP. Escalate to a separate OS user *only if* Kun's canary shows the cua path cannot be confined to the desktop-control lease, or shared-desktop contention otherwise blocks the required reads (the T3.5 / T4.1 residual).

## 2. Broker/lease architecture (Q5)

**Invariant (no-lease-no-action).** Every automation action — capture, navigate, click, type, close, submit, clipboard, focus — is refused unless the caller presents a *live lease whose scope covers the exact target and every global resource the action touches*, and the target's identity **re-verifies** at action time. This is enforced at the driver wrapper (cua-driver / CDP client), so an un-brokered call cannot reach the OS.

**Lease scopes.** Two families:
- **Target leases** — hierarchical, single-writer: `{browser-bundle → user-data-dir → window-id → tab/target-id}`. A write lease is exclusive at its leaf; a target may have at most one writer. Read leases may be shared but are still recorded (needed for the §3 freeze and the T3.5 observer canary).
- **Global-resource leases** — strictly single-holder, machine-wide. The umbrella is the **desktop-control lease** (a.k.a. cua-write lease): one exclusive lease over the whole shared desktop surface — **screen, keyboard, pointer, accessibility tree, and recording machinery** — that **every cua/AX/pointer/keyboard write must hold** (T4.1, T4.3, T4.5). Because "Two agents clicking at once still contend for the same desktop" (T4.3), only one holder may perform a cua/desktop write at a time across *all* agents; browser-native DOM/CDP writes (T4.5) are exempt and need only their target lease. It subsumes `keyboard`/`focus` for the cua path (T3.2, evidence 19). Alongside it: **clipboard** (banned by default, else leased with compare-restore — T3.3), **downloads-dir** (per-lease — T2.5), and the **account-submission lease** (§3). Because these are OS-global (G3, T3.2, T3.3), desktop-global (T4.1, T4.3), or account-global (T5.2), the broker grants at most one holder each across *all* agents. **Window-confinement invariant (operator hard boundary, Duho 2026-07-15):** the desktop-control lease authorizes cua/AX/pointer/keyboard writes **only inside the leased browser/Flow window** — holding it is *not* license to click the desktop. Every action re-verifies the resolved target app == the leased browser bundle (see fail-closed, below); if it resolves to the macOS menu bar, Dock, Finder, or **System Settings/Preferences**, the broker **denies, fails closed, and STOPS → hands to Duho**. OS-level permission requirements are never satisfied by automation.

**Lease record (contract fields).** `lease-id`; `holder {agent, pid}`; `scope` (the tuple above); `target-fingerprint` (bundle id + `user-data-dir` path + native `window-id` + CDP `target-id` + last-known URL/origin hash); `granted-at`; `ttl`; `heartbeat-interval`; `epoch` (monotonic fence token); `state ∈ {live, expired, revoked}`.

**Single-writer exclusivity.** The broker's registry rejects a second write lease on any target whose fingerprint overlaps a live one, and rejects any global-resource lease already held. cua-driver's native key is `{pid, window_id, element_index}` (T4.1); since a *tab* is **not** a durable cua target (T4.2), a `tab/target-id` lease MUST be backed by a CDP `target-id` (T1.4), never by cua alone.

**TTL + heartbeat + revocation.** A lease is valid only while `now < granted-at + ttl` **and** the holder has heartbeat within `heartbeat-interval`. A missed heartbeat expires the lease; the broker may also revoke (e.g., §3 account freeze). Every action carries the lease `epoch`; the broker rejects any action bearing a stale epoch (fencing against a revoked-then-resumed client).

**Fail-closed on lease loss — the R1/R2 lesson.** Before *every* action the client re-verifies the leased target fingerprint: PID alive, native `window-id` still present, CDP `target-id` still enumerable with matching URL/origin hash (T1.4), **and the owning app bundle == the leased browser — never `com.apple.systempreferences` (System Settings), Finder, or the menu bar** (operator hard boundary). If any element fails to resolve — the exact G4/T4.4 signature (`list_apps=0`, `0x0` capture while doctor is GREEN) — the client **STOPS, releases the lease, and raises a bridge-loss event. It MUST NOT fall back to the frontmost window/active tab** (the current G1a behavior is prohibited). Fail-closed defaults: unresolved identity → deny; expired/absent lease → deny; ambiguous target → deny; **resolved target outside the leased browser window (System Settings / menu bar / Finder / Dock) → deny + STOP + hand to Duho**.

**Audit journal.** Append-only. One record per grant / heartbeat / re-verify / action / revoke / release / bridge-loss, each stamped with lease-id, epoch, target-fingerprint, and (for captures) an evidence hash — the receipt substrate for Kun's byte-comparable canary assertions.

**cua-driver compatibility & the parallelism ceiling.** cua's background `{pid, window_id, element_index}` addressing routes an action to a target without moving the foreground (T4.1) — but routing is **not an independent desktop channel**: multiple MCP clients "still share the same screen, keyboard, pointer, accessibility tree, and recording machinery" and "Two agents clicking at once still contend" (T4.1, T4.3, Cua Driver 0.7.1, evidence 20). Therefore every cua/AX/pointer/keyboard action executes **only while holding the exclusive desktop-control lease** — serialized machine-wide, no `activate`. **The sole parallel-write path is browser-native DOM/CDP** — "For a browser TAB the reliable path is the `page` tool (drives the DOM via CDP)" (T4.5) — over separate browser processes/profiles. Durable tab identity is cua-UNKNOWN (T4.2), so tab-level leases require CDP target-ids (T1.4). **Desktop-control-lease loss fails closed exactly like target-lease loss** (above) — never a frontmost fallback. The whole broker is gated behind Kun's C0 dual-bridge soak, which must now *also* prove that two connected cua sessions sharing the desktop do not corrupt each other even at idle (T4.1, T4.3), before any live use.

## 3. Authenticated-session & shared-state policy (Q3)

1. **Same-Google-account concurrency.** Process/profile *parallelism* is allowed (distinct instances/profiles are officially isolable — T1.2), **but authenticated submissions are serialized at the account level: at most one authenticated surface is "active" (submitting) per account at a time.** Official support for concurrent same-account automated sessions is **UNKNOWN** (T5.1, T5.3); until Tori's evidence shows otherwise, serialize. This is enforced by the single-holder **account-submission lease** (§2).
2. **Quota coupling.** Credits are account-wide "regardless of which device you use" (T5.2) and Gemini/Deep Research draw compute-based limits (T5.3). Parallelism does **not** multiply quota; the broker treats credits as one shared pool — the account-submission lease also serves as the budget gate, and no boundary (§1) relaxes this.
3. **Downloads segregation.** Every browser lease owns a dedicated `downloadsPath` (T2.5); the shared `~/Downloads` sink (G3 `:L148`) is banned for leased automation. No two leases share a download dir.
4. **Clipboard.** The general pasteboard is **banned** for automation — it is "shared by all running apps" (T3.3) and the current `set the clipboard` (G1c) is an exclusive global write. Text goes in via per-target injection (CDP `insertText` / element-addressed input, T2.1/T1.4/T4.1). *If* a genuine clipboard path is ever unavoidable, it requires the single-holder clipboard lease with save-hash → set → use → restore → verify-hash semantics (T3.3).
5. **Focus discipline.** No `activate` outside a held **focus lease** (current G1b `activate` is banned). Default path is background input that never moves the foreground (T4.1); a focus lease is required only when foreground is genuinely unavoidable, and must snapshot and restore the prior frontmost app. A focus lease may foreground **only** the leased browser/Flow window — never System Settings, Finder, or any OS surface (§3.7).
6. **Permission-prompt / CAPTCHA / account-challenge = conservative wide hard-stop.** Any native permission dialog, reCAPTCHA/"unusual traffic" (T5.4), or account challenge is a **freeze event**: the broker immediately suspends **all** leases that share the same Google account **and** the same egress/network as the trigger — not just the triggering agent. This wide freeze is a **conservative policy chosen because the challenge scope is UNKNOWN**, not a claim that the trigger is account-level: the only VERIFIED signal is that Google Search unusual-traffic is network/egress-driven (T5.4), and Flow/Gemini challenge scope is unestablished (T5.3, T5.4). Resume requires a fresh user gate. Encountering one = do-not-interact, freeze, and **STOP → hand to Duho**; OS-level permissions are granted only by a human, never navigated or toggled by automation.
