# THE MANIFEST MUST BE CHECKABLE BY A PERSON — owner decision (2026-09-07 16:23 KST)
The assembled `INPUT_MANIFEST_A1.json` carries **1,529 file entries and 359 placeholders**; `RUNTIME_DEPENDENCIES_A1_FINAL.json` carries 1,521 files and 422 dyld-loaded images. That is the whole library surface, not the run path's inputs, and it defeats the rule it was built to satisfy.
My Q5 decision was: *the manifest lists exactly the files the run path reads, each with SHA-256; a file the run path reads that is absent from the manifest is a defect — and that is the test.* The test only works if a human can run it. Nobody can eyeball 1,529 rows and 359 placeholders and say whether the freeze is honest; the two entries that actually matter — the eligible-id file and the derived failed-set file — are buried in it.

**DECIDED, two registers with different jobs:**
1. **INPUT MANIFEST — short and human-checkable.** The run path's DATA INPUTS (eligible ids, failed set, dry-run exclusions, render coordinates, brick table, no-r registry, render config, protected region) and OUR CODE (select_sample.py, run_path.py, medium_perturbation.py, verify_drand_v2.py, fourier_chirality.py, the renderer modules, validation_gate.py, env_lock.json). Each with a real digest. Placeholders ONLY for what genuinely cannot exist yet, each naming the stage that produces it. Expected size: tens of entries, not thousands.
2. **RUNTIME ENVIRONMENT — pinned by its own mechanism, not by sweeping site-packages.** The interpreter and its digest, library VERSIONS, the env_lock values the driver already enforces, and the specific extension modules the driver checks. A per-file digest sweep of an installed library tree is neither stable across environments nor verifiable at freeze time; claiming it as a pin would be a claim we cannot honour.
The exhaustive sweep is RETAINED as an inventory artefact — it is real data and it cost nothing to keep — but it is NOT the manifest, and `ready_for_input_freeze` must not be computed from it.
