## C. NEW DEFECTS

**F18 FATAL**: §7.11 claims "35 receipts precede the commit timestamp". This is a factual error. A count of the live `tier_c_fetch_receipts.jsonl` shows exactly 42 receipts with a `"utc"` timestamp prior to `2026-09-02T05:30:32Z` (the ad21829fa commit).
*Repair*: Change "35" to "42" in both places it appears in §7.11.

**F19 FATAL**: §7.11's content re-hash checks the on-disk file against "that receipt's `computed_sha256` and its `published_sha256`." It never checks the independent NERSC `.sha256sum` source. Because the receipt was generated by the script itself, a compromised script could write a fake `published_sha256` that matches a tampered brick, defeating the integrity gate.
*Repair*: Require the content re-hash to securely fetch or pin the NERSC checksum source and compare the on-disk file hash to the actual NERSC checksum, rather than solely trusting the receipt's copy.

**F20 FATAL**: The 17,947-file content re-hash reads files and produces a chained receipt with `manifest_count`, `files_checked`, and `mismatches`. However, these fields are not added to the verdict program's schema in §16.7b, nor checked by `concordance_verdict.py`. Thus, the re-hash result is never bound to the machine-checkable pixel-access gate.
*Repair*: Either (a) update the verdict program schema and logic to require `mismatches == 0` and `files_checked == 17947` from the seal receipt, or (b) explicitly state that the seal seat MUST pass `data_integrity_pass = false` to the verdict program if the programmatic re-hash fails.

**F21 MINOR**: §7.11 states, "Git alone cannot witness which working-tree bytes ran during those minutes." This phrase wrongly implies Git is a partial witness for the 2m48s gap. Git did not witness the gap at all, as the commit happened after.
*Repair*: Change the phrasing to "Git does not witness which working-tree bytes ran during those minutes."
