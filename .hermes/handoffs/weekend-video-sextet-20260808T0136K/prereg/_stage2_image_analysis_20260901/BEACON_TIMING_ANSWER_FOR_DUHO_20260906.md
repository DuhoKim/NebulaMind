# Is the beacon timing time-critical? — answer to Duho's question (relay 09:06 KST, 2026-09-06)

Question only; nothing executed. Quotes are from the signed V15 (`OPTION_A_INSTRUMENT_SELECTION_RULE_DRAFT_V15_20260906.md`, digest fdd9eedd…), §3b unless stated; line numbers are the file's.

1. **T_pulse.** The signed text says (§3b line 32): "T_pulse = the first whole minute ≥ T_sign + 600 s". With T_sign = 2026-09-06T00:04:07Z: T_sign + 600 s = 00:14:07Z; first whole minute at or after it = **2026-09-06T00:15:00Z = 09:15 KST today**.

2. **Deadline to read it.** The signed text is SILENT on a deadline: the words deadline, lapse, window, expire, "must be read", "no later than" do not occur. What it does say (line 32): the collector "REFUSES to run before T_pulse (observed BEACON-NOT-YET)"; and (line 35) the outcome is computed from "now" relative to T_pulse. My reading: an unread pulse WAITS. NIST archives every pulse and drand relays serve historic rounds, so the pulse for T_pulse can be collected at any later time; nothing lapses. Line 58 adds that "a signed rule with a passed T_pulse and no filed identity is itself a visible event" — a transparency point, not a penalty.

3. **By when must he decide.** Nothing lapses or degrades, so there is no such moment. The only timestamp that matters is in item 4.

4. **The 24-hour clock.** The signed text says (line 35): "RETRY when the primary is not authenticable or not retrievable and now < T_pulse + 24 h — never a seed; from T_pulse + 24 h, if the primary is still not authenticable NOW (recomputed live, not read) … the FALLBACK: drand". The reference is T_pulse, not the first fetch. So it is a fixed instant, already determined by his signature: **2026-09-07T00:15:00Z = 09:15 KST Monday**. It "started" in the sense that it is fixed; nothing happens at that instant by itself. It only decides what a later collection yields: before it, RETRY (no seed); after it, drand if NIST still does not authenticate, NIST if it does.

5. **Would waiting help NIST verify?** The signed text says (line 38 (i)): NIST's served certificate "holds a 2048-bit key against a 512-byte signature; under this rule that pulse is REFUSED and, if NIST still serves a non-verifying certificate 24 h after T_pulse, the fallback applies — whether NIST fixes this is outside our control". My reading: it is a standing property of what NIST serves for chain 2 (one certificate per chain signs every pulse; a 512-byte signature means a 4096-bit signing key, so the served certificate does not match the key that signs). A later pulse on the same chain would fail the same way until NIST changes the certificate. I have ONE live sample (pulse 1928259, 2026-09-05T15:13Z); I do not know whether NIST will change it, and I cannot exclude that our certificate lookup reaches the wrong certificate — that is the open finding in decision 4.

6. **Worst case if he answers in three days.** Under the signed text, a collection on 09-09 gives: NIST archived pulse re-fetched live, refused (non-verifying) → past T_pulse + 24 h → drand round ⌊(T_pulse − 1595431050)/30⌋ + 1 from the four pinned relays, ACCEPT-DRAND if at least two agree. Nothing breaks; the seed is the same value it would be tomorrow. The one unrecoverable case is UNAVAILABLE (fewer than two pinned relays returning that historic round): "never a seed", and the signed text is silent on what follows — my reading is that it would take a new signature (new T_sign) and Duho's ruling, because the text names no second attempt. Delay does not create that risk (historic rounds stay served) but marginally lengthens exposure to relay outages. If NIST changed its certificate before the read, NIST becomes binding instead — not a break.

**Bottom line:** not time-critical. Decision 4 can wait; the only fixed instant is 09:15 KST Monday, after which the fallback path is what the rule will follow if NIST is unchanged.
