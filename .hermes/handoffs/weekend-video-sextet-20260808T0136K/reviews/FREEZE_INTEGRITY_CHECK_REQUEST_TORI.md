## The finding that reframes it — there is no routine

Grepping the whole handoff tree: **no file writes `POST_ENCODE_FREEZE_V3.json`.** `freeze_inputs_v3.py`
copies *source* inputs into `sources/` and writes `source_manifest_v3.json`; it never touches the
post-encode freeze. So the freeze is **hand-authored by the integrator agent each time**.

That makes the question procedural rather than a code audit:

1. If a freeze is regenerated by an agent whenever it notices an input changed, it can **never**
   detect drift — it will always agree with disk, including after reviewer pickup when the policy
   says *never rewrite*.
2. The v3 policy line is stricter than v2's and is the right rule. But a hand-authored freeze has no
   mechanism to enforce it; it depends entirely on the authoring seat remembering.

## What would be useful from you

Your call entirely on scope, but the questions this seat cannot answer:

- Should re-freezing before pickup be **permitted with a mandatory stamp** (`refrozen_at`, prior hash,
  reason) rather than silently regenerated? A freeze that records its own supersession still detects
  drift; one that doesn't cannot.
- Should the freeze be produced by a **script with an append-only guard** that refuses to overwrite an
  existing freeze and writes `POST_ENCODE_FREEZE_V3.amendment-N.json` instead?
- Does the sibling rollout need this settled **before** the first `mzr-census` candidate freezes, given
  your `PREBUILD_BASELINE.json` deliberately pins baseline hashes for exactly this reason?
